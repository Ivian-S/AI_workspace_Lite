## 2. 已建立的核心模型

当前 CLI：

```text
Terminal
→ argparse / main.py
→ ProjectService
→ JsonProjectStorage
→ data/projects.json
```

未来 HTTP：

```text
Client
→ HTTP Request
→ FastAPI Router
→ ProjectService
→ Storage
→ HTTP Response
```

关键设计结论：

- HTTP 是请求/响应协议；REST 是架构风格，两者不是同一个概念。
- Method 表达客户端意图，URL / request target 表达操作目标。
- Header 描述 HTTP 消息的元数据；Body 承载请求或响应内容。
- JSON 是常见的 HTTP 表示格式，但 JSON 不等于 HTTP。
- HTTP Status Code 与 CLI exit code 属于不同协议边界，不能机械一一映射。
- REST API 优先围绕资源设计，例如 `/projects`，而不是把动作写进 URL。
- 当前 `Project` 没有 `id`，因此本任务按 `name` 作为资源标识，不虚构不存在的字段。
- 当前 `update_project()` 是完整替换语义，更接近 `PUT`；路线中的 `PATCH` 部分更新留到后续任务正式处理。
- `ProjectService` 继续负责业务规则；Router 未来负责 HTTP 与 Python/业务层之间的协议翻译。

## 3. 无 AI 验收结果

### A. HTTP 拆解

给定请求：

```http
POST /projects HTTP/1.1
Host: 127.0.0.1:8000
Content-Type: application/json
Accept: application/json

{
  "name": "llm-paper",
  "tags": ["ai", "research"]
}
```

验收答案：

```text
Method:
POST

request target:
/projects

Headers:
Host: 127.0.0.1:8000
Content-Type: application/json
Accept: application/json

Body:
{
  "name": "llm-paper",
  "tags": ["ai", "research"]
}

客户端意图：
向 /projects 资源集合提交数据，请求 Server 创建一个新的 Project。
```

**结果：✅ 通过**

精度修正：

- `Host` 更严谨地表示请求的目标主机，以及可选端口；它在 HTTP/1.1 中也支持虚拟主机等场景。
- `Content-Type: application/json` 表示当前请求 Body 使用 JSON 表示。
- `Accept: application/json` 表示客户端希望响应优先使用 JSON 表示。

### B. REST 设计

```text
创建 Project
→ POST /projects

获取所有 Projects
→ GET /projects

获取名为 demo 的 Project
→ GET /projects/demo

完整替换名为 demo 的 Project
→ PUT /projects/demo

删除名为 demo 的 Project
→ DELETE /projects/demo
```

**结果：✅ 全部正确**

本题严格忠于当前模型：Project 尚无 `id`，继续使用 `name` 标识资源。

### C. Status Code 判断

```text
查询成功
→ 200 OK

创建成功
→ 201 Created

删除成功且不返回 Body
→ 204 No Content

Project 不存在
→ 404 Not Found

创建重名 Project
→ 409 Conflict

未处理 Python Bug
→ 500 Internal Server Error
```

**结果：✅ 全部正确**

补充：

`201 Created` 响应常见可以提供 `Location` 指向新资源，但 `Location` 不是所有 201 响应都必须存在的条件。

### D. 数据流口述

当前 CLI 创建 Project：

```text
用户输入命令
→ argparse / main.py 解析参数
→ main.py 调用 ProjectService.create_project(...)
→ Service 执行业务规则并构造 Project
→ JsonProjectStorage 持久化
→ Service 返回 Project
→ main.py 格式化并输出到终端
```

未来 HTTP 创建 Project：

```text
Client 发送 POST /projects + JSON Body
→ FastAPI / Router 接收 HTTP 请求并获得请求数据
→ Router 调用 ProjectService.create_project(...)
→ Service 执行业务规则
→ Storage 持久化
→ Service 返回 Project 或抛出业务异常
→ HTTP 边界把结果/异常转换为 Status Code + JSON Response
→ 返回 Client
```

为什么保留 `ProjectService`：

```text
ProjectService
→ 业务规则，与 CLI / HTTP 等输入输出方式无关

Router
→ HTTP 协议边界，把请求转换为业务调用，
  再把业务结果或异常转换为 HTTP 响应
```

**结果：✅ 通过**

这里已经正确区分了：

```text
协议职责
≠
业务职责
```

这是后续 FastAPI 分层的关键地基。

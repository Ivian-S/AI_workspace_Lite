## 2. 核心概念图解

### 2.1 当前包结构

```text
project/                      ← 当前工作目录 / 项目根目录
├── app/                     ← Python package
│   ├── __init__.py
│   ├── main.py
│   ├── models.py
│   ├── services.py
│   ├── storage.py
│   └── _import_lab.py       ← 本任务导入实验模块
└── tests/
```

`app/` 中存在 `__init__.py`，因此当前项目明确把它作为普通 Python package 使用。

---

### 2.2 使用 `-m` 执行模块

执行：

```bash
.venv/bin/python -m app._import_lab
```

观察结果：

```text
__name__ = __main__
__package__ = app
Project = <class 'app.models.Project'>
```

数据流：

```text
项目根目录
   │
   │ python -m app._import_lab
   ▼
Python 先按模块名解析 app._import_lab
   │
   ├── 确认父 package = app
   │
   └── 设置 __package__ = "app"
   ▼
from .models import Project
   │
   ▼
解析为 app.models
   │
   ▼
导入成功
```

关键点不是“用了 `-m` 就更高级”，而是：

> Python 以 **package 中的模块** 身份执行 `_import_lab.py`，因此相对导入拥有明确的父 package 上下文。

---

### 2.3 直接执行文件

执行：

```bash
.venv/bin/python app/_import_lab.py
```

结果：

```text
ImportError: attempted relative import with no known parent package
```

当前 `_import_lab.py` 中存在：

```python
from .models import Project
```

直接把文件当脚本运行时，Python 没有把它作为 `app._import_lab` 这个包内模块来执行，因此相对导入缺少可用于解析 `.` 的父 package。

核心关系：

```text
python app/_import_lab.py
        │
        ▼
按“脚本文件”执行
        │
        ▼
没有可靠的父 package 上下文
        │
        ▼
from .models ...
        │
        ▼
无法确定 "." 指向哪个 package
        │
        ▼
ImportError
```

因此，多文件 package 内模块应优先从项目根目录使用模块方式启动，例如：

```bash
python -m app.main
```

而不是依赖：

```bash
python app/main.py
```

---

### 2.4 模块搜索路径

执行：

```bash
.venv/bin/python -c "import sys; print(sys.path)"
```

观察到：

```text
[
    '',
    ... Python 标准库路径 ...,
    ... site-packages ...
]
```

这里需要特别修正一个容易误解的点：

> `sys.path` 中的空字符串 `''` 在这种 `python -c` 场景下代表 **当前工作目录**，并不是“项目根目录没有出现”。

本次命令从：

```text
~/projects/Learn1/project
```

执行，因此当前工作目录就是项目根目录，`import app` 可以从这里找到：

```text
project/app/
```

排查 `ModuleNotFoundError` 时应该问：

```text
1. 我当前从哪个目录启动 Python？
2. sys.path 实际包含哪些搜索入口？
3. 目标 package / module 是否位于其中某个入口下面？
4. 是否被同名模块遮蔽？
```

---

### 2.5 确认实际导入位置

执行：

```bash
.venv/bin/python -c "import app; print(app.__file__)"
```

结果：

```text
/home/dev/projects/Learn1/project/app/__init__.py
```

这证明当前：

```python
import app
```

加载的是本项目的 `app` package。

这是非常实用的排错动作，可以识别：

- 导入了环境里另一个同名 package；
- 当前工作目录不符合预期；
- 本地文件名遮蔽第三方包；
- editable install / 环境配置导致导入位置与预期不同。

---

### 2.6 探测模块是否可解析

执行：

```bash
.venv/bin/python -c "import importlib.util; print(importlib.util.find_spec('app.models'))"
```

结果中的：

```text
origin='/home/dev/projects/Learn1/project/app/models.py'
```

说明 Python 当前能够解析：

```text
app.models
```

并且最终定位到本项目：

```text
app/models.py
```

`find_spec()` 很适合回答：

```text
“Python 到底能不能找到这个模块？”
```

但它不能自动替代所有导入排错；模块执行期间仍可能因为循环导入、模块内部异常等原因失败。

### 4.2 当前依赖方向

现阶段核心模块依赖关系可以简化为：

```text
main
 │
 ▼
services
 ├────────► models
 │
 └────────► storage
              │
              └────► models
```

应避免：

```text
models ─────► services
   ▲           │
   └───────────┘
```

否则会同时产生：

1. import 依赖环；
2. 模块职责反向耦合。

## 5. 避坑指南与 Code Review 修正

### 5.1 修正一：循环导入不一定“直接抛 ImportError”

原回答中：

```text
形成循环导入环，触发模块半初始化报错
```

方向正确，但表述过于绝对。

更准确的是：

> 循环导入会让某个模块在尚未完成顶层代码执行时被另一个模块再次引用。**如果此时访问了尚未创建的名称**，常见结果是 `ImportError` 或 `AttributeError`，错误信息通常会提到 `partially initialized module`。但并不是所有循环导入都会在所有写法下立刻失败。

例如，以下风险很高：

```python
# services.py
from app.models import Project

# models.py
from app.services import ProjectService
```

因为双方都可能在模块初始化过程中立即索取对方尚未定义完成的名字。

因此排错时不要只记：

```text
循环导入 = 必然 ImportError
```

而应该理解：

```text
循环依赖
→ 模块初始化顺序互相依赖
→ 某些名字可能在被访问时尚不存在
→ 出现 partially initialized module 相关错误
```

---

### 5.2 修正二：不要把分层表述机械记成“高层依赖低层”

原回答：

```text
高层（Service）依赖低层（Model），低层不能反向依赖高层
```

在当前项目语境下，想表达的依赖方向是对的，但“高层 / 低层”这组词容易与后续依赖倒置原则混淆。

当前阶段更准确的说法是：

> **在 AI Workspace Lite 当前职责设计中，Service 可以使用 Model；Model 只表达 Project 数据，不应该为了业务动作反向 import Service。**

也就是：

```text
Service → Model      ✅ 当前允许
Model → Service      ❌ 当前不应该
```

原因首先是模块职责，而不是背诵“哪层高、哪层低”。

以后学习依赖倒置时还会出现：

```text
高层策略不应该直接依赖低层实现细节
```

因此现在避免把两个概念混成一句口诀。

---

### 5.3 修正三：`sys.path` 中的 `''` 要会解释

原回答说：

```text
检查项目根目录是否在搜索路径里
```

这个方向没问题，但这次实际输出没有直接打印：

```text
/home/dev/projects/Learn1/project
```

而是：

```text
''
```

这里不能误判为“项目根目录不在 sys.path”。

本次 `python -c` 中：

```text
'' → 当前工作目录
```

当前工作目录正是：

```text
/home/dev/projects/Learn1/project
```

所以 `app` 能被正常发现。

---

### 5.4 `ModuleNotFoundError` 的最小排错顺序

以后遇到：

```text
ModuleNotFoundError: No module named 'xxx'
```

优先按这个顺序：

```text
① pwd
   ↓
确认当前从哪里启动

② python -c "import sys; print(sys.path)"
   ↓
确认 Python 去哪里找模块

③ python -c "import xxx; print(xxx.__file__)"
   ↓
如果能导入，确认实际加载位置

④ importlib.util.find_spec(...)
   ↓
探测目标模块能否被解析

⑤ 检查启动方式
   python file.py
   vs
   python -m package.module

⑥ 检查文件 / package 名称
   ↓
拼写、同名遮蔽、__init__.py、安装环境

⑦ 再检查循环导入
```

不要第一反应就是：

```python
sys.path.append(...)
```

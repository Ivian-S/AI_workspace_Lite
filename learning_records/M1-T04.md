## 4. 代码变更

### 新增：`app/storage.py`

新增：

```python
class InMemoryProjectStorage:
    ...
```

内部维护：

```python
self._projects: list[Project]
```

当前提供：

```text
save(project)
list_all()
get_by_name(name)
```

#### `save()`

负责将 Project 保存到内存列表。

#### `list_all()`

不直接返回：

```python
self._projects
```

而是返回：

```python
list(self._projects)
```

这样调用者得到的是新的外层 list，不会因为：

```python
projects.clear()
```

直接清空 Storage 内部 collection。

需要注意：

```text
只复制外层 list
```

其中的 Project 对象仍然可以是相同对象。

本任务没有使用 `deepcopy()`，因为当前没有要求完全隔离 Project 对象本身。

#### `get_by_name()`

独立验收任务中新增：

```python
def get_by_name(
    self,
    name: str,
) -> Project | None:
    ...
```

遍历：

```python
self._projects
```

存在匹配名称：

```text
返回 Project
```

不存在：

```text
返回 None
```

真正与 `_projects` 打交道的查询逻辑位于 Storage，而不是 Service。

---

### 新增：`app/services.py`

新增：

```python
class ProjectService:
    ...
```

通过构造函数接收 Storage：

```python
ProjectService(storage)
```

并保存：

```python
self._storage = storage
```

这建立了：

```text
ProjectService HAS-A Storage
```

而不是：

```text
ProjectService IS-A Storage
```

因此使用组合，而不是继承。

当前主要接口：

```text
create_project(...)
list_projects()
get_project(name)
```

#### `create_project()`

负责：

```text
接收业务输入
→ 创建 Project
→ 调用 Storage 保存
→ 返回 Project
```

Service 自身不维护 `_projects`。

#### `list_projects()`

将数据读取职责委托给：

```text
storage.list_all()
```

#### `get_project()`

独立验收任务新增：

```python
def get_project(
    self,
    name: str,
) -> Project | None:
    return self._storage.get_by_name(name)
```

Service 不直接：

```text
访问 storage._projects
遍历 list
判断底层存储结构
```

而是把具体查询操作交给 Storage。

## 5. 组合与继承

本任务确认：

```text
组合 = has-a
继承 = is-a
```

ProjectService 与 Storage 的真实关系是：

```text
ProjectService 使用一个 Storage
```

而不是：

```text
ProjectService 是一种 Storage
```

因此不应该设计：

```python
class ProjectService(InMemoryProjectStorage):
    ...
```

否则会造成：

* Service 和存储职责混合；
* Service 暴露不应该属于自己的存储操作；
* Service 与具体存储实现产生更强耦合；
* 后续更换存储方式更加困难。

当前采用：

```python
class ProjectService:
    def __init__(self, storage: InMemoryProjectStorage) -> None:
        self._storage = storage
```

表达组合关系更加准确。

## 6. 具体实现与抽象接口

本任务 Code Review 中进一步确认：

虽然当前已经使用：

```text
组合
+
构造函数传入依赖
```

但还不能说：

```text
ProjectService 已经依赖抽象接口
```

原因是当前类型注解仍然明确写成：

```python
storage: InMemoryProjectStorage
```

`InMemoryProjectStorage` 是具体实现类。

因此当前状态是：

```text
组合                         ✅
构造函数传入 Storage          ✅
Service 与存储状态分离         ✅
Service 不访问 _projects       ✅

统一 Storage 抽象             ❌
Protocol / ABC               ❌
完整依赖倒置                  ❌
```

这些没有实现不是缺陷，而是当前阶段刻意控制复杂度的结果。

以后出现多个真实 Storage 实现以后，再评估共同抽象。

## 7. JSON Storage 的正确演进认知

未来如果需要 JSON 持久化，不应该直接把：

```python
InMemoryProjectStorage
```

内部改造成 JSON 文件读写。

因为：

```text
InMemoryProjectStorage
```

这个名称已经表达：

```text
它是一种内存存储实现
```

更合理的演进概念上应该是：

```text
Storage implementations

├── InMemoryProjectStorage
│      └── list[Project]
│
└── JsonProjectStorage
       └── JSON file
```

两种实现可以拥有相同或兼容的存取行为，但保留各自明确的存储语义。

当前仍有一个已知设计限制：

```python
ProjectService(
    storage: InMemoryProjectStorage,
)
```

类型注解直接绑定具体实现。

Python 运行时不会因为这个类型注解自动禁止传入其他兼容对象，但静态类型检查会认为其他 Storage 类型不匹配。

因此未来真正需要支持多种 Storage 时，需要重新设计共同的 Storage 类型契约。

当前不提前实现 `Protocol` 或 ABC。

## 8. Model invariant 与 Service business rule

本任务 Code Review 中重点澄清：

不能简单记忆：

```text
校验全部放 Service
```

应该根据规则本身的含义判断。

### Model invariant

如果规则表达：

```text
任何合法 Project
在任何时候都必须满足这个条件
```

那么它属于模型不变量。

例如：

```text
任何合法 Project 的 name 永远不能是空字符串
```

如果这是系统对 Project 的定义，那么可以考虑由 Model 保证。

例如未来可能通过：

```python
__post_init__()
```

建立这种约束。

### Service business rule

如果规则依赖：

```text
某个业务动作
外部状态
操作上下文
其他 Project
当前用户
```

则更加适合 Service。

例如：

```text
创建项目时
名称不能与已经存在的项目重复
```

这个判断需要查询其他项目，因此不是 Project 单个对象自身能够判断的不变量。

### Storage

Storage 主要负责：

```text
怎么保存
怎么读取
怎么查找
```

不应该成为业务规则的主要归属位置。

## 9. `frozen=True` 与数据校验

本任务确认：

```python
@dataclass(frozen=True)
```

主要限制：

```text
对象创建以后不能正常重新给字段赋值
```

例如：

```python
project.name = "new"
```

会受到限制。

但：

```text
frozen=True
```

不会自动检查：

```text
name 是否为空
name 长度是否合法
字符串格式是否合法
```

因此：

```python
Project(name="")
```

不会仅仅因为 `frozen=True` 就被判断为非法。

如果未来 Model 需要保证类似不变量，可以通过显式校验逻辑实现，例如 `__post_init__`。

异常的正式设计与自定义业务异常不在本卡实现，留到 M1-T06。

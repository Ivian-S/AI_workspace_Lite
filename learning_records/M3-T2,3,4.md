## 4. 主键、唯一约束与外键验收

### 4.1 users

实际数据库结构确认：

```text
id         integer                  NOT NULL
username   varchar(64)              NOT NULL
email      varchar(320)             NOT NULL
created_at timestamp with time zone NOT NULL DEFAULT now()
```

约束：

```text
users_pkey         PRIMARY KEY (id)
users_email_key    UNIQUE (email)
users_username_key UNIQUE (username)
```

并被以下表引用：

```text
files.uploaded_by_user_id
operation_logs.actor_user_id
workspace_members.user_id
workspaces.owner_user_id
```

说明已经建立：

```text
稳定数据库身份 → users.id
业务唯一属性   → username / email UNIQUE
```

结果：✅

### 4.2 workspace_members

实际确认：

```text
PRIMARY KEY (workspace_id, user_id)
```

并存在：

```text
workspace_id → workspaces.id
user_id      → users.id
```

这证明 User ↔ Workspace 的多对多关系已经通过中间表落到关系数据库，而不是继续使用 Python `list[str]` 表达成员关系。

结果：✅

### 4.3 projects

实际确认：

```text
id           PRIMARY KEY
workspace_id NOT NULL
name         NOT NULL
```

约束：

```text
FOREIGN KEY (workspace_id)
→ workspaces(id)

UNIQUE (workspace_id, name)
```

因此：

```text
不同 Workspace
→ 可以拥有相同项目名

同一 Workspace
→ 项目名不能重复
```

这也完成了从 M1/M2：

```text
Project.name ≈ 查找身份
```

向：

```text
Project.id          → 稳定数据库身份
Project.name        → 业务属性
Project.workspace_id → Workspace 边界
```

的模型升级。

结果：✅

### 4.4 tasks

实际确认：

```text
id           PRIMARY KEY
workspace_id NOT NULL
project_id   NULLABLE
title        NOT NULL
status       NOT NULL DEFAULT 'todo'
```

外键：

```text

```

## 5. Foreign Key 真实失败实验

实际执行：

```sql
INSERT INTO projects (workspace_id, name)
VALUES (999999, 'should-fail');
```

PostgreSQL 实际返回：

```text
ERROR:
insert or update on table "projects"
violates foreign key constraint "projects_workspace_id_fkey"

DETAIL:
Key (workspace_id)=(999999)
is not present in table "workspaces".
```

这个实验非常关键，因为当时没有：

```text
FastAPI
Service
Repository
Python if
```

仍然由数据库直接拒绝非法引用。

因此已经实际验证：

```text
Foreign Key
→ 数据库级引用完整性
```

同时必须保留边界：

```text
Foreign Key
≠ 用户权限检查
```

FK 只能证明引用的数据存在，不能证明当前请求用户有权访问它。

结果：✅

## 6. SQLAlchemy Session 生命周期实验

### 6.1 add 后尚未获得数据库主键

实际操作：

```python
session = SessionLocal()

user = UserRow(
    username="m3_demo",
    email="m3_demo@example.com",
)

session.add(user)

print(user.id)
```

实际结果：

```text
None
```

说明：

```text
session.add()
→ ORM 对象进入 Session 管理
→ 不等于事务已经永久写入数据库
```

### 6.2 flush 后数据库生成主键

实际执行：

```python
session.flush()
print(user.id)
```

实际结果：

```text
1
```

证明：

```text
Session
→ flush
→ SQLAlchemy 发送 INSERT
→ PostgreSQL 生成 id
→ ORM 对象获得数据库主键
```

### 6.3 完整 Session 验收脚本

完整实验结果：

```text
before flush: None
after flush: 2
loaded: 2 m3_t234_demo m3_t234_demo@example.com
```

因此实际走通：

```text
UserRow(...)
→ session.add()
→ pending
→ session.flush()
→ INSERT
→ PostgreSQL 生成 id
→ session.commit()
→ 新 Session
→ SELECT / ORM load
→ session.delete()
→ commit()
```

结果：✅

## 7. ORM / Database 关键认知

本任务形成以下边界：

### Engine

```text
数据库连接基础设施
→ SQLAlchemy 与 PostgreSQL Driver 的入口
```

### Session

```text
一次数据库工作单元
→ 跟踪 ORM Object 状态
→ 管理 flush / transaction / commit
```

### ForeignKey

```text
数据库 Schema 层约束
```

### relationship()

```text
Python ORM 对象导航关系
```

因此：

```text
relationship()
≠ ForeignKey
```

### create_all()

本卡通过：

```text
Base.metadata.create_all(...)
```

完成首次空数据库 bootstrap。

但：

```text
create_all()
≠ Migration
```

已有 Schema 的版本演进、ALTER TABLE 和升级历史属于后续 M3-T06。

## 8. 当前已知设计限制

### 8.1 Task 的 Workspace / Project 一致性

当前 Task 同时包含：

```text
workspace_id
project_id
```

两个独立 FK 可以分别证明：

```text
Workspace 存在
Project 存在
```

但数据库目前不能仅凭这两个独立 FK 保证：

```text
project_id 对应的 Project
一定属于 task.workspace_id 对应的 Workspace
```

这是当前 MVP 已知限制。

后续可以选择：

```text
Service / Repository 显式校验
```

或进一步升级为：

```text
组合唯一约束 + Composite Foreign Key
```

当前不为了这一点提前扩大 ORM 复杂度。

### 8.2 Workspace owner 与 membership 的业务不变量

Schema 同时存在：

```text
workspaces.owner_user_id
workspace_members(workspace_id, user_id, role)
```

未来创建 Workspace 时必须保证：

```text
owner_user_id
↔ workspace_members 中对应 user
↔ role = 'owner'
```

否则可能出现：

```text
Workspace 有 owner
但 owner 不在成员表
```

这一不变量应在后续 Service / Transaction 中保证，不需要现在重设计表。

### 8.3 role / status 目前是字符串

当前：

```text
workspace_members.role
tasks.status
```

使用字符串字段。

后续如果业务状态稳定，可以考虑：

```text
CheckConstraint
或应用层枚举 + 数据库约束
```

当前不提前增加状态机复杂度。

## 9. 小型环境清理建议

第一次手工 Session 实验中：

```text
m3_demo
```

已经执行 `session.commit()`。

后面的完整验收脚本清理的是：

```text
m3_t234_demo
```

因此学习数据库中很可能仍保留：

```text
m3_demo
```

这不会影响任务正确性，也不阻塞验收。

如希望保持学习数据库整洁，可执行：

```sql
DELETE FROM users
WHERE username = 'm3_demo';
```

随后验证：

```sql
SELECT id, username, email
FROM users
ORDER BY id;
```
(已执行并删除)
注意即使删除该用户，PostgreSQL sequence 出现 id 空洞也是正常行为；主键只需要稳定唯一，不要求连续。

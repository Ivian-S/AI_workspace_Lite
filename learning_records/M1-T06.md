## 2. 核心数据流

### 2.1 Storage 层

```text
ProjectService
    │
    │ storage.get_by_name(name)
    ▼
InMemoryProjectStorage
    │
    ├── 找到
    │     └── return Project
    │
    └── 未找到
          └── return None
```

Storage 的职责仍然是描述存储查询结果，因此：

```python
Project | None
```

是合理接口。

### 2.2 Service 层

```text
ProjectService.get_project(name)
    │
    ▼
storage.get_by_name(name)
    │
    ├── Project
    │      └── return Project
    │
    └── None
           └── raise ProjectNotFoundError(name)
```

Service 对外表达的是一个业务动作：

```text
“给我这个 Project”
```

因此不存在时不再把 `None` 当作正常结果交给调用者，而是转换为明确失败。

## 3. 代码变更

### 新增：`app/exceptions.py`

```python
class ProjectNotFoundError(Exception):
    def __init__(self, project_name: str) -> None:
        self.project_name = project_name
        super().__init__(f"Project not found: {project_name}")
```

设计结论：

- 当前只有一个真实业务异常，不建立多层异常继承树；
- 保存 `project_name`，调用者无需从错误字符串反向解析业务数据；
- 继承 `Exception` 对当前阶段足够清晰。

### 修改：`app/services.py`

`ProjectService.get_project()` 修改为：

```python
def get_project(self, name: str) -> Project:
    project = self._storage.get_by_name(name)

    if project is None:
        raise ProjectNotFoundError(name)

    return project
```

接口语义从：

```text
Project | None
```

变为：

```text
成功
→ Project

失败
→ ProjectNotFoundError
```

Storage 不修改，仍负责底层查询；Service 不直接访问 `storage._projects`。

### 修改：`tests/test_services.py`

原 M1-T04 测试：

```text
项目不存在
→ 返回 None
```

修改为：

```python
def test_get_project_raises_when_project_not_found() -> None:
    storage = InMemoryProjectStorage()
    service = ProjectService(storage)

    with pytest.raises(
        ProjectNotFoundError,
        match="Project not found: missing",
    ):
        service.get_project("missing")
```

该测试同时验证：

- 异常类型必须是 `ProjectNotFoundError`；
- 异常信息包含目标项目名称；
- Service 不再以 `None` 表示该业务失败。

### Review 4：问题回答 1

原回答核心正确：

> Storage 回答存储里是否存在数据，空结果是查询事实；Service 表达业务动作，失败时转为异常。

通过。

更严格地说：

```text
Storage.get_by_name()
→ 查询操作允许“无结果”

Service.get_project()
→ 正常返回契约收紧为 Project
→ 无结果走异常控制流
```

### Review 5：问题回答 2

原回答主体正确，但需要一处修正：

```text
raise
```

并不保证上层一定存在 `except`。

更准确的表述：

```text
raise
→ 中断当前正常控制流
→ 沿调用栈向上传播
→ 如果某一层有匹配的 except，则在那里处理
→ 如果一直没人处理，则传播到程序顶层并表现为未处理异常
```

因此不能把 `raise` 简化成“把控制权交给 except”。

### Review 6：问题回答 3

原回答：

> `except Exception` 会吞掉所有异常。

这里需要技术修正。

`except Exception:` **不会捕获所有 Python 异常**。

例如以下类型直接继承自 `BaseException` 而不是 `Exception`：

```text
KeyboardInterrupt
SystemExit
GeneratorExit
```

因此更准确的是：

> `except Exception:` 会捕获绝大多数普通运行时异常，包括 `AttributeError`、`TypeError`、`ValueError` 等。若随后直接返回 `None`，很容易把真正的程序 Bug 伪装成业务空结果。

本题真正的工程风险判断仍然正确。

### Review 7：问题回答 4

通过。

原回答正确抓住了两个关键风险：

```text
随意返回默认值
→ 伪造正常完成
→ 错误远离原始故障位置
```

以及：

```text
继续传播
→ 让真正有能力处理的上层边界处理
→ 保留异常上下文和 traceback
```

“快速失败”可以作为理解辅助，但不要机械理解成“所有异常都越早崩溃越好”；如果当前层能够可靠恢复、转换或补充必要上下文，合理捕获仍然是正确行为。

## 5. 异常处理原则总结

### `return None`

```text
函数正常完成
→ 返回值恰好为空
```

适合表达：

```text
查询可能没有结果
```

### `raise`

```text
当前正常路径无法完成
→ 中断
→ 异常向上传播
```

适合表达明确失败。

### `except SpecificError`

推荐：

```python
try:
    ...
except ProjectNotFoundError:
    ...
```

前提是当前层知道怎样处理这个失败。

### `except Exception`

不是裸 `except`，但通常太宽：

```python
try:
    ...
except Exception:
    return None
```

会把大量普通程序错误静默转换为业务默认值，应非常谨慎。

### 裸 `except`

不允许：

```python
try:
    ...
except:
    ...
```

它连 `KeyboardInterrupt`、`SystemExit` 等 `BaseException` 子类也可能捕获，会严重破坏调试和正常退出行为。

## 9. 本任务关键工程经验

M1-T06 最重要的变化不是多了一个异常类，而是开始区分：

```text
“没有查到”
```

和：

```text
“业务动作失败”
```

二者不必由同一层用同一种方式表达。

当前设计：

```text
Storage：
查询不到
→ None

Service：
业务对象不存在
→ ProjectNotFoundError
```

同时建立异常处理原则：

```text
能真正处理
→ 捕获

不能处理
→ 继续传播

不要用宽泛 except 把 Bug 转换成默认值
```

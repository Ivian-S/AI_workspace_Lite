## 3. middleware 与异常传播

middleware 对未知异常采用：

```python
except Exception as exc:
    logger.error(...)
    raise
```

这里的含义是：

```text
观察异常
→ 记录请求上下文
→ 重新抛出原异常
```

因此未知异常仍会正常传播，由服务器按照 500 类错误处理。

它与下面这种错误做法完全不同：

```python
except Exception:
    return JSONResponse(status_code=404, ...)
```

后者会吞掉服务器 Bug 并错误翻译为客户端错误。

## 6. 临时 500 故障实验

临时 Route：

```text
GET /debug/m2-t07-boom
```

触发：

```python
raise RuntimeError(
    "M2-T07 intentional failure"
)
```

### middleware 实际日志

实际记录：

```text
ERROR:
request_failed
method=GET
path=/debug/m2-t07-boom
duration_ms=1.06
error_type=RuntimeError
```

结果：✅

这证明 middleware 的：

```python
except Exception:
    logger.error(...)
    raise
```

确实捕获到了未知异常用于观察，并保留了原异常类型。

### HTTP 实际结果

Uvicorn access log：

```text
GET /debug/m2-t07-boom HTTP/1.1
500 Internal Server Error
```

结果：✅

未知异常没有被转换成 404 / 409，而是保持服务器错误语义。

### traceback 实际定位

traceback 中首先可以看到 middleware 自己代码的位置：

```text
app/main.py
line 82
log_http_request
response = await call_next(request)
```

继续沿 traceback 向下找到真正的业务代码来源：

```text
app/main.py
line 67
debug_m2_t07_boom
raise RuntimeError(...)
```

最终异常：

```text
RuntimeError: M2-T07 intentional failure
```

结果：✅

因此本次已经实际完成：

```text
500
→ request_failed
→ error_type=RuntimeError
→ HTTP 500
→ traceback
→ app/main.py:67
→ debug_m2_t07_boom
```

这不是根据概念推测，而是实际服务器输出。

## 7. traceback 的正确阅读方式

这次 traceback 中包含大量：

```text
uvicorn/
starlette/
fastapi/
anyio/
```

框架调用栈。

排错时不能停在：

```text
看到很多框架文件
→ 认为是 FastAPI 出错
```

正确顺序：

```text
1. 看 traceback 最终异常类型
   RuntimeError

2. 看最终异常消息
   M2-T07 intentional failure

3. 从下往上寻找自己项目路径
   /home/dev/projects/Learn1/project/app/main.py

4. 找到真正抛出异常的最内层自己代码
   line 67
   debug_m2_t07_boom

5. 再向上理解异常如何经过 middleware
   line 82
   log_http_request
```

因此：

```text
main.py:82
```

不是根因。

它只是：

```text
middleware 正在等待下游请求处理
```

真正根因是：

```text
main.py:67
raise RuntimeError(...)
```

这一区别是 M2-T07 的核心排错能力。

## 8. 当前完整排错模型

```text
先看 HTTP Status
        │
        ▼
看 Method + Path
        │
        ▼
判断 Route 是否匹配
        │
        ├─ 422
        │   → validation_error
        │   → loc=path/query/body
        │
        ├─ 404
        │   → 有 business_error？
        │      ├─ 无 → routing 404
        │      └─ 有 → business 404
        │
        ├─ 409
        │   → business_error type/detail
        │
        └─ 500
            → request_failed.error_type
            → traceback
            → 找自己项目文件
            → 找真正抛异常的最内层行号
```

## 2. 数据流与设计变化

### M1-T02 数据结构

此前 Project 使用裸字典：

```python
{
    "name": name,
    "tags": [],
    "members": [],
}
```

这种形式适合学习：

* 对象引用；
* `dict` 可变性；
* 嵌套 `list`；
* 浅拷贝；
* 原地修改。

但数据结构本身缺少明确约束，字段名称和预期类型主要依赖开发者记忆。

### M1-T03 数据结构

本任务新增 `Project` dataclass：

```python
@dataclass
class Project:
    name: str
    description: str | None = None
    tags: list[str] = field(default_factory=list)
    members: list[str] = field(default_factory=list)
```

Project 因此从：

```text
任意 dict
```

演进为：

```text
Project
├── name: str
├── description: str | None
├── tags: list[str]
└── members: list[str]
```

代码访问方式也从：

```python
project["name"]
project["tags"]
```

调整为：

```python
project.name
project.tags
```

### 创建 Project 的数据流

```text
调用者
  │
  ├── name
  ├── description
  ├── tags
  └── members
  │
  ▼
create_project()
  │
  ├── tags is None → 创建新列表
  ├── tags 有值 → 复制输入列表
  ├── members is None → 创建新列表
  └── members 有值 → 复制输入列表
  │
  ▼
Project(...)
  │
  ▼
返回 Project 对象
```

外部传入的可变列表不会直接成为 Project 的内部列表，从而避免调用者后续修改输入列表时污染 Project 内部状态。

## 3. 代码变更

### 新增：`app/models.py`

新增 `Project` 数据模型：

```python
from dataclasses import dataclass, field


@dataclass
class Project:
    name: str
    description: str | None = None
    tags: list[str] = field(default_factory=list)
    members: list[str] = field(default_factory=list)
```

关键设计：

* `name` 明确为 `str`；
* `description` 为可选字符串；
* `description` 默认值为 `None`；
* `tags` 和 `members` 使用 `default_factory=list`；
* 不让多个 Project 实例共享同一个默认列表。

---

### 修改：`app/project_state.py`

#### `create_project()`

函数接口增加类型注解，并返回 `Project`：

```python
def create_project(
    name: str,
    description: str | None = None,
    tags: list[str] | None = None,
    members: list[str] | None = None,
) -> Project:
    ...
```

该函数负责：

* 接收 Project 初始化数据；
* 正确处理 `None`；
* 为传入的可变列表建立独立副本；
* 创建并返回 `Project`。

#### `add_tag_in_place()`

接口明确为：

```python
def add_tag_in_place(
    project: Project,
    tag: str,
) -> None:
```

其设计意图是：

```text
接收已有 Project
→ 原地修改 project.tags
→ 不创建新的 Project
```

`-> None` 能直接表达函数存在原地修改行为，而不是返回新的业务对象。

#### `with_tag()`

接口明确为：

```python
def with_tag(
    project: Project,
    tag: str,
) -> Project:
```

其设计意图是：

```text
读取原 Project
→ 创建新的 tags
→ 创建新的 Project
→ 原 Project 保持不变
```

Code Review 中发现增加 `description` 字段以后，最初的 `with_tag()` 没有同步复制该字段，会造成新 Project 的 `description` 丢失。

该问题已通过回归测试修正。

这是本任务最重要的工程经验之一：

> 数据模型增加字段以后，必须检查所有“创建副本”“克隆对象”“重新构造对象”的代码路径。

#### `clone_project()`

继续保持显式复制策略：

* 创建新的 Project；
* `name` 与 `description` 保留原值；
* `tags` 创建新的 list；
* `members` 创建新的 list。

当前没有使用 `deepcopy()`，因为现有结构足够简单，可以明确判断哪些可变字段需要隔离。

## 6. 核心知识理解

### 6.1 `field(default_factory=list)` 为什么必要

Project 的 `tags` 和 `members` 属于可变对象。

需求不是让不同 Project 共享同一个列表，而是：

```text
每创建一个 Project
→ 创建一个新的 list
```

因此使用：

```python
field(default_factory=list)
```

`default_factory` 会在每次实例化 Project 时调用 `list()`，使不同实例获得彼此独立的列表。

同时，dataclass 本身会阻止直接使用典型的可变默认列表作为字段默认值。

---

### 6.2 类型注解不是运行时数据校验

例如：

```python
name: str
```

主要表达：

```text
这个位置设计上应该是字符串
```

它服务于：

* 开发者阅读；
* IDE 提示；
* 静态类型检查工具；
* 函数接口理解。

普通 Python 类型注解本身不会自动提供完整的运行时输入校验。

因此：

```python
Project(name=123)
```

不能简单理解成一定会因为 `name: str` 而被 Python 自动拒绝。

真正的 HTTP 输入校验将在后续 FastAPI / Pydantic 阶段处理。

---

### 6.3 `-> None` 与 `-> Project`

```python
def add_tag_in_place(...) -> None
```

表达：

```text
函数直接修改传入的 Project
不返回新的业务对象
```

而：

```python
def with_tag(...) -> Project
```

表达：

```text
函数根据原 Project 创建并返回新的 Project
```

类型签名不仅描述类型，也帮助阅读者理解函数设计。

---

### 6.4 为什么复制调用者传入的列表

如果 Project 直接保存调用者传入的 `tags`：

```text
外部变量 ───┐
            ├── 同一个 list
Project ────┘
```

那么调用者以后执行：

```python
tags.append(...)
```

可能无意中修改 Project 内部状态。

复制后变为：

```text
外部 tags ───► list A

Project.tags ─► list B
```

二者状态隔离。

本任务因此进一步确认：

> 对于外部传入的可变对象，需要明确决定是共享引用还是复制，不能无意识地共享状态。

## 7. Code Review 记录

### Review 发现 1：新增字段造成复制路径数据丢失

增加 `description` 后，最初版本的：

```python
with_tag()
```

重新构造 Project 时没有复制 `description`。

这意味着：

```text
原 Project.description 有值
→ with_tag()
→ 新 Project.description 变回 None
```

属于真实的数据丢失回归。

解决方式：

* 修正 `with_tag()`；
* 增加 `test_with_tag_preserves_description` 回归测试。

最终测试通过。

### Review 发现 2：测试断言虽然绿色，但验证力度不足

原引用测试中的某个断言只验证：

```text
修改后的值 != "Changed"
```

并不能精确证明两个变量确实观察到了同一对象的状态变化。

修正后测试明确验证：

* `project_a is project_b`；
* 修改 `project_b` 后，`project_a` 能观察到相同结果。

经验：

> 测试不仅要通过，还要检查断言是否真的验证了需求。

### Review 发现 3：类型语法和对象构造不要混淆

本任务中进一步区分：

```python
list[str]
```

与：

```python
list(...)
```

前者主要表达：

```text
字符串列表这一类型
```

后者用于：

```text
实际创建一个新的 list 对象
```

后续代码应优先保持这两个职责清晰。

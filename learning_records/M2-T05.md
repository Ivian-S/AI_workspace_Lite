### Create

```text
POST /projects
→ JSON Request Body
→ Pydantic Request Schema
→ create_project_api()
→ ProjectService.create_project()
→ JsonProjectStorage.save()
→ data/projects.json
→ Project
→ ProjectResponse
→ HTTP 201 Created
```

### List

```text
GET /projects
→ list_projects_api()
→ ProjectService.list_projects()
→ JsonProjectStorage.list_all()
→ list[Project]
→ list[ProjectResponse]
→ HTTP 200 OK
```

### Get One

```text
GET /projects/{project_name}
→ Path Parameter
→ get_project_api()
→ ProjectService.get_project(project_name)
→ JsonProjectStorage.get_by_name()
→ Project
→ ProjectResponse
→ HTTP 200 OK
```

### Patch

```text
PATCH /projects/{project_name}
→ Path Parameter + ProjectUpdateRequest
→ body.model_dump(exclude_unset=True)
→ 读取当前 Project
→ 将客户端实际传入的字段与现有字段合并
→ ProjectService.update_project(...)
→ JsonProjectStorage.update_by_name(...)
→ ProjectResponse
→ HTTP 200 OK
```

### Delete

```text
DELETE /projects/{project_name}
→ delete_project_api()
→ ProjectService.delete_project(project_name)
→ JsonProjectStorage.delete_by_name()
→ HTTP 204 No Content
```

## 4. PATCH 的核心知识点

本卡最重要的代码语义之一：

```python
body.model_dump(exclude_unset=True)
```

作用是只提取客户端实际发送过的字段。

例如当前 Project：

```json
{
  "name": "patch-test",
  "description": "before",
  "tags": ["a"],
  "members": ["alice"]
}
```

客户端只发送：

```json
{
  "description": "after"
}
```

那么 PATCH 不能把未发送的字段自动覆盖成默认值或 `None`，最终必须保留：

```text
name = "patch-test"
tags = ["a"]
members = ["alice"]
```

同时需要区分：

```text
字段没传
```

和：

```json
{
  "description": null
}
```

前者表示“不修改 description”，后者表示客户端明确希望把 description 设置为 `None`。

本次无 AI 验收中已经能够正确解释：

```text
exclude_unset=True
→ 区分“没传”与“传 null”
→ 防止 PATCH 用默认值覆盖未修改字段
```

## 5. Router / Service 职责

本次能够正确说明：

```text
项目重名
→ 业务规则
→ ProjectService 负责
```

Route 不应复制：

```text
先 list
→ 自己查重
→ 再决定是否创建
```

而应直接：

```text
Route
→ ProjectService.create_project()
```

原因：

```text
同一业务规则可能同时被 CLI / Web / 后续其他入口复用；
业务规则只保留在 Service，才能避免不同入口行为不一致。
```

这也是本项目第一次真正实现：

```text
Client
→ Router
→ Service
→ Storage
```

完整分层调用链。

## 8. 本次输出中的采集污染

与 M2-T04 类似，本次终端输出再次出现下一条命令覆盖上一条 curl 响应正文的情况。

例如记录中出现类似：

```text
"description":"created from HTTPcurl -i ...
```

以及：

```text
"tags":["curl -i ...
```

这些字符串显然不是正常 API 返回的 JSON 内容，而是终端文本采集 / 光标覆盖造成的污染。

因此正式验收不把这些脏字符串当作真实业务数据。

仍可可靠确认的证据包括：

```text
HTTP Status Code
Content-Type
Content-Length
后续 CRUD 操作能继续成功
用户独立 PATCH 保留字段验收
OpenAPI smoke tests
```

建议以后采集 curl 输出时，每条命令单独执行并确保上一条输出结束后再粘贴下一条；如果要留验收记录，可以把每条命令输出重定向到独立文件，避免终端覆盖影响阅读。
